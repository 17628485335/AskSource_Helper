# 长期记忆系统实施计划

> 日期：2026-11-28  
> 状态：待评审 / 待实施  
> 关联文档：`docs/context-memory-execution-plan.md`（会话内压缩记忆）  
> 范围：跨 session 的用户长期记忆；不与会话压缩摘要混用。

---

## 0. 一条主线

写入与读取分开设计：

- **写入**：工具显式写入 + 后台异步抽取，两条路径共用一个存储。
- **读取**：高重要度记忆自动注入，检索只作为兜底。
- **触发**：以 `turn` 为单位，不在 `model call` 上触发。
- **执行**：异步入队，缓冲批处理；强信号插队；session 结束保底。

一句话概括：

> 写：工具管“用户明确要记的”，抽取管“没说但值得记的”；读：默认自动注入，检索只当保底；触发用 turn 不用 model call，异步 + 缓冲 + 强信号插队。

---

## 1. 边界与非目标

### 1.1 长期记忆解决什么

长期记忆保存跨 session 仍然有效的信息：

- 用户稳定偏好：例如“回答用中文”“偏好 Python 3.12”。
- 用户稳定事实：例如“我在做 AskSource 项目”“团队用 FastAPI + Vue”。
- 有有效期的重要事件：例如“下周要上线 v2”。

它解决的是：

> 下次会话仍然记得用户和项目背景。

### 1.2 不解决什么

- 不替代会话内压缩摘要。压缩摘要负责把当前 session 变短；长期记忆负责跨 session 保留事实。
- 不把每次会话摘要自动写成长期记忆。只有稳定、可复用、跨会话有价值的信息才进入长期记忆。
- P0 的记忆粒度是 `agent_id + user_id`（`user_id=0` 表示 agent 全局），不是纯 agent 级；人工管理已有入口：设置 → Agent → 预设，不需要等 P3 新建面板。
- 多租户隔离（`tenant_id`）仍留到 P3。
- 不把“要不要检索记忆”的判断完全交给模型。模型不知道自己有什么记忆，容易不调或乱调。

## 2. 总体架构

```text
写入侧
  用户显式要求 / 纠正 / 偏好
        │
        ▼
  save_memory 工具 ──────┐
                         │
  turn 完成事件 ──► 队列 ─┼──► 去重合并 ──► agent_memories（agent_id + user_id）
        │                │
        └─ 强信号插队 ────┘

读取侧
  session 开始 / 每轮
        │
        ├─ 自动注入高重要度记忆（稳定位置）
        │
        └─ search_memory(query) 兜底（后置、低占比）
```

核心原则：**写入要准，读取要稳**。写入宁可少写、可更新，也不要碎片化堆积；读取宁可固定注入少量高价值内容，也不要每轮靠模型自己决定检索。

## 3. 写入设计

### 3.1 三条写入路径，共用一个存储

| 路径 | 负责什么 | 触发方式 | 备注 |
| --- | --- | --- | --- |
| 显式工具 `save_memory` | 用户明确要求“记住”、纠正错误、透露稳定偏好 | 模型主动调用 | 语义准，但调用率天然低；需在 SystemMessage 中写明触发条件 |
| 后台抽取 | 用户未明说但值得保留的信息 | turn 结束异步触发 | 作为保底，避免遗漏 |
| 人工 / 管理接口 | 修正错误、批量清理 | 设置 → Agent → 预设 | 入口已存在，不需要新建面板 |

三条路径写入同一个 `agent_memories` 表，按 `agent_id + user_id` 隔离。工具写入和抽取写入必须合并：

- 用 `content hash` 做精确去重。
- 用语义相似度做近似去重。
- 同一 `type` + 高相似度 → 走 `update`，不要各存一份。

### 3.2 工具接口设计

工具提供四个操作：

| 操作 | 用途 |
| --- | --- |
| `add` | 新增一条长期记忆 |
| `update` | 修正已有记忆内容或重要性 |
| `delete` | 删除过期、错误或被用户否定的记忆 |
| `search` | 模型在明确感觉缺信息时主动检索 |

`update` 和 `delete` 比 `add` 更重要：记忆会过期、会写错。只提供 `add` 会把 `agent_memories` 变成只增不减的垃圾场。

#### 安全约束

- `user_id` / `tenant_id` 必须由框架注入。
- 绝不允许模型传入 `user_id` / `tenant_id`，防止提示词注入导致跨用户写入或读取。
- 工具层返回的必须是**已落库结果的回显**，不是“即将写入”。

#### 必带字段

- `type`：`preference` / `fact` / `event`。
- `importance`：`0~1`。

#### 返回回显

工具返回示例：

```text
已记录：用户偏好 Python 3.12。
```

模型看到确认回显后，才不容易在同一轮或后续轮重复写入相同内容。

## 4. 触发时机

### 4.1 三个层级

| 层级 | 含义 | 一轮内次数 |
| --- | --- | --- |
| `model call` | 单次 LLM 请求，含工具调用后的再调用 | 3~10 |
| `turn` | 用户一条消息 → agent 最终答复 | 1 |
| `session` | 整个会话 | 1 |

### 4.2 为什么不能挂到 model call

- 频率高：一轮可能有 3~10 次模型调用。
- 中间态没有完整语义：工具调用后的中间消息不代表用户意图。
- 同一轮多次写入会造成碎片冲突和重复。
- 成本和写入噪音都会放大。

结论：**触发粒度必须是 turn，不是 model call。**

### 4.3 推荐触发链路

```text
用户消息
  → agent 给出最终 answer
  → turn 结束事件入队
  → 缓冲：累积 N 轮 或 token 超阈值
  → 批量抽取
  → 去重合并
  → 写 agent_memories
```

### 4.4 缓冲规则

| 规则 | 说明 |
| --- | --- |
| 默认缓冲 N 轮 | 3~5 轮；省成本，上下文更厚，抽取质量更高 |
| token 超阈值 | 防止长对话上下文过大 |
| 强信号插队 | “记住” / 纠正 / 偏好 → 跳过缓冲立即抽取，否则体验上是 bug |
| session 结束保底 | 补齐尾部，避免未达阈值的记忆丢失 |

## 5. 读取设计

### 5.1 核心问题

模型不知道自己有什么记忆，所以“要不要检索”这个决策它做不好：

- 不调：等于没有记忆。
- 乱调：污染上下文，增加延迟和 token。

因此不能把长期记忆做成“必须调用”的工具。

### 5.2 读取层级

| 层级 | 做法 | 说明 |
| --- | --- | --- |
| 主路径 | 会话开始 / 每轮把高重要度记忆直接拼进 system 区 | 默认生效，不依赖模型判断 |
| 辅助路径 | `search_memory(query)` 仅在模型明确感觉缺信息时使用 | 作为兜底，不作为主路径 |
| 保底方案 | 分层：常驻少量核心画像 + 检索补充 | 控制 token，同时保留召回能力 |

### 5.3 上下文位置约束

长期记忆拼接位置要尽量稳定，才能命中前缀缓存。

- 稳定核心画像：放在 system 区固定位置，内容尽量少变。
- 按 query 重算的检索结果：属于高变动内容，必须后置，不能放在 system 开头。
- 自动注入内容需要预算上限，避免挤占当前会话上下文。

## 6. 数据结构

### 6.1 当前表：`agent_memories`

长期记忆直接复用现有的 `agent_memories` 表，不新建 memory store，也不复用 `chat_summaries`。记忆粒度为 `agent_id + user_id`：`user_id=0` 表示 agent 全局记忆，非 0 表示只属于该用户。

| 字段 | 当前状态 | 与方案的关系 |
| --- | --- | --- |
| `id` | 已有 | 满足 |
| `agent_id` | 已有，FK `agents.id` | 满足 agent 维度 |
| `user_id` | 已加，默认 `0`，带索引 | 满足 `agent + user_id` 粒度 |
| `content` | 已有，`Text` | 满足 |
| `enabled` | 已有，`bool` | 满足启停，但不能替代 `importance` / `type` |
| `created_at` / `updated_at` | 已有 | 满足 |
| `type` | 无 | 需要补：`preference` / `fact` / `event` |
| `importance` | 无 | 需要补：决定自动注入优先级 |
| `source` | 无 | 需要补：`tool` / `extractor` / `manual`，影响冲突权重 |
| `hash` | 无 | 需要补：精确去重 |
| `turn_id` | 无 | P1 需要：抽取幂等标记 |
| `ttl` | 无 | P2 需要：`event` 类过期清理 |
| `tenant_id` | 无 | P3 需要：多租户隔离 |

结论：**表结构还需要改**。`user_id` 已补齐；建议本次把 `type` / `importance` / `source` / `hash` / `turn_id` / `ttl` 一并补上，全部给可空或默认值，避免后续多次迁移。`tenant_id` 留到 P3。

### 6.2 目标单条结构

```json
{
  "id": 123,
  "agent_id": 7,
  "user_id": 3,
  "type": "preference",
  "content": "用户偏好回答使用中文，且尽量简洁",
  "importance": 0.9,
  "source": "tool",
  "turn_id": 456,
  "hash": "sha256:...",
  "enabled": true,
  "created_at": "2026-11-28T10:00:00+08:00",
  "updated_at": "2026-11-28T10:00:00+08:00",
  "ttl": null
}
```

其中 `user_id=0` 表示 agent 全局记忆；非 0 时只对该用户生效。

### 6.3 字段说明

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `agent_id` | agent 归属，框架/管理端注入 |
| `user_id` | 用户归属；`0` = agent 全局，非 0 = 用户专属 |
| `type` | `preference` / `fact` / `event` |
| `content` | 记忆正文 |
| `importance` | `0~1`，影响自动注入优先级 |
| `source` | `tool` / `extractor` / `manual` |
| `turn_id` | 来源 turn，幂等标记；可复用 `chat_turns.id` |
| `hash` | 内容指纹，用于精确去重 |
| `enabled` | 是否启用；人工面板可直接停用 |
| `created_at` | 创建时间 |
| `updated_at` | 最近更新时间 |
| `ttl` | 有效期；`event` 类必填，`preference` 类为空 |
| `tenant_id` | 多租户阶段启用，框架注入 |

### 6.4 类型约束

- `preference`：长期保存，除非用户明确否定或更新。
- `fact`：长期保存，但可被更新。
- `event`：必须设置 TTL，过期后不再注入。

没有类型划分，记忆库半年后就会积累大量无效内容。

## 7. 工程细节

### 7.1 抽取器必须看到已有记忆

抽取器 prompt 必须带上 top-K 相关旧记忆。否则它分不清应该：

- `add`：确实是新信息。
- `update`：是旧信息的新版本。
- `delete`：旧信息已被否定。
- 忽略：只是重复。

### 7.2 幂等

- 每 turn 生成 `turn_id`。
- 抽取结果打上来源 `turn_id`。
- 重试或重放不会重复写。
- 唯一约束建议：`(user_id, turn_id, hash)` 或 `(user_id, type, hash)`。

### 7.3 冲突处理

- 同一 `type` + 高语义相似度 → 走 `update`。
- 保留 `updated_at`，覆盖旧值。
- 用户显式纠正优先于后台抽取结果。
- 显式工具的权重高于 extractor。

### 7.4 与上下文工程对齐

- 自动注入内容要稳定，尽量命中前缀缓存。
- 检索结果属于高变动内容，后置拼接。
- 注入预算单独计算，避免挤占会话历史和压缩摘要。
- 长期记忆读取口径应纳入 context usage 估算，避免显示值与实际送入模型不一致。

## 8. 分阶段实施

### P0：最小闭环

| 项 | 内容 |
| --- | --- |
| 触发条件 | `agent_id + user_id` 粒度，记忆 < 200 条 |
| 目标 | 自动注入 + 一个 `save_memory` 工具即可；人工维护复用设置 → Agent → 预设 |
| 工作 | 复用 `agent_memories` 表并按 6.1 补齐字段；实现 `add/update/delete/search`；实现高重要度记忆自动注入；SystemMessage 写明工具触发条件 |
| 不做 | 后台抽取、TTL 清理、多租户 |
| 验收 | 用户明确要求记住后能跨 session 命中；重复写入被 hash 去重；记忆注入位置稳定 |

### P1：补齐遗漏

| 项 | 内容 |
| --- | --- |
| 触发条件 | 工具调用率低 / 有遗漏 |
| 目标 | 加 turn 级异步抽取 + 去重合并 |
| 工作 | turn 结束事件；队列与缓冲；批量抽取；top-K 旧记忆进 prompt；强信号插队；session 结束保底 |
| 验收 | 未明说但稳定的偏好能被抽取；同一事实不重复落库；抽取不阻塞对话主链路 |

### P2：规模化召回

| 项 | 内容 |
| --- | --- |
| 触发条件 | 记忆量上千 |
| 目标 | 加 `search_memory`、分层召回、TTL 清理 |
| 工作 | 向量或混合检索；核心画像常驻 + 检索补充；event TTL 清理；重要性衰减；注入预算控制 |
| 验收 | 高重要度命中稳定；低重要度不污染上下文；过期 event 不再注入 |

### P3：多租户与治理

| 项 | 内容 |
| --- | --- |
| 触发条件 | 多租户 |
| 目标 | 多租户隔离、权限、审计、批量治理 |
| 工作 | `tenant_id` 隔离；权限校验；变更审计；批量清理增强；删除传播（人工面板 P0 已可用） |
| 验收 | 越权读写为 0；所有变更可追溯；用户可修正或删除错误记忆 |

## 9. 风险与指标

### 9.1 主要风险

| 风险 | 表现 | 缓解 |
| --- | --- | --- |
| 误写 | 临时情绪、一次性要求被写成长期偏好 | 强类型 + importance 阈值 + 后台抽取确认 |
| 重复 | 工具和抽取各存一份 | hash + 语义相似度 + update 优先 |
| 过期 | 旧事实长期污染上下文 | event TTL + importance 衰减 + delete 工具 |
| 污染上下文 | 检索结果过多或过杂 | 主路径自动注入，检索后置且限量 |
| 跨用户写入 | 提示词注入伪造 user_id | user_id / tenant_id 框架注入 |
| 缓存失效 | 每轮拼接内容变化 | 核心画像稳定前置，检索结果后置 |

### 9.2 建议指标

- 写入准确率：抽取出的记忆中真实有效的比例。
- 重复率：同一事实在 store 中重复出现的比例。
- 检索命中率：需要记忆时能注入正确记忆的比例。
- 注入 token 占比：长期记忆占实际上下文的比例。
- 写入延迟：从 turn 结束到记忆可读取的时间。
- 越权事件数：必须为 0。

## 10. 与当前代码的关系

- 会话压缩（`chat_summaries`）继续负责当前 session 的上下文压缩。
- 长期记忆复用现有 `agent_memories` 表，按 `agent_id + user_id` 隔离；不复用 `chat_summaries`。
- 长期记忆读取时要纳入 `context usage` 估算口径，避免出现“界面显示估算，实际又多注入一段记忆”的偏差。
- `turn_id` 可直接复用 `chat_turns.id`，保证幂等和来源可追溯。
- 自动注入内容应进入 `app.context.history` 或独立的 memory assembler，但仍由 `chat_manager.astream` 统一拼到上下文头部。

---

## 11. 结论

长期记忆的关键不是“能不能存”，而是：

1. **写入要分路径**：明确要求走工具，隐含信息走抽取，二者合并去重。
2. **触发要按 turn**：不能挂 model call，中间态没有完整语义。
3. **读取要默认注入**：检索只是兜底，不让模型承担“知不知道自己有什么记忆”的判断。
4. **结构要可治理**：复用 `agent_memories`，按 `agent_id + user_id` 隔离；type、importance、TTL、hash、turn_id 缺一不可。
5. **工程要可演进**：P0 先闭环，P1 补抽取，P2 做召回，P3 做治理。
